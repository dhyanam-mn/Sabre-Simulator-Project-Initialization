1. WHAT WE ARE DOING (one paragraph)
------------------------------------------------------------------------------------------
We build a deterministic Python simulator of a CPU, run FCFS / SJF / RR / Priority / MLFQ /
RR+StaticThreshold and our SABRE scheduler on identical fake workloads, inject three attacks
(fork bomb, CPU hog, low-and-slow) plus an adaptive attacker, and measure performance, detection
and collateral damage. SABRE = predicted burst + behaviour class + class-conditional risk score
-> queue, quantum, share cap. Containment is graduated (levels 0-3), reversible, never starving
and work-conserving. Output: 9-10 experiments, plots, statistics, and a paper.

Verdict: the plan is solid and already better than most student projects (novelty list N1-N7,
30 seeds, paired tests, ablation, charged overhead). To make it a RESEARCH project it needs:
a threat model, a few formal guarantees, stronger baselines, real-data validation, robustness
tests and a reproducibility package. Also 8 concrete flaws in the spec must be fixed first.

2. FLAWS / RISKS FOUND IN THE CURRENT SPEC (fix before coding)
------------------------------------------------------------------------------------------
F1 [MUST] A hog can look like a legitimate CPU-bound process.
   Class-conditional risk judges a process against its own class. A hog is classified
   cpu_bound (share ~0.9+, no IO), and the spec says a benign cpu_bound at 0.9 share must stay
   level 0. So z_cpu ~ 0 and the hog may never be flagged. What separates them is burst length:
   benign cpu_bound bursts are lognormal (mean 150 ms), the hog's burst never ends.
   FIX: add features `burst_age_ms` (CPU run since last IO/burst end) and `slices_since_io`;
   calibrate per-class mu/sigma (or p99) for them; add signal s_age = clip((age - p99_class)/
   scale,0,1) into the noisy-OR. Update Features dataclass NOW (before interfaces freeze).
   Write this as an explicit "identifiability" paragraph in the paper: what is and is not
   separable from scheduler-visible data.

F2 [MUST] Calibration circularity.
   Baselines mu/sigma are learned under RR but applied while SABRE changes quanta (shares
   differ). FIX: calibrate under SABRE with use_risk=false (same scheduler, risk off); report
   RR-calibrated vs SABRE-calibrated as a sensitivity result.

F3 [MUST] Fork-bomb children inflate detection metrics.
   label=1 for up to 2000 forkchildren means process-level recall/precision measure mostly the
   children. FIX: report BOTH process-level and attack-instance-level (a tree counts as
   detected when root or any descendant reaches level>=2; TTD = first flag in tree minus attack
   start). Primary security metric = instance-level.

F4 [MUST] LSI / ADI definitions are inconsistent and can divide by zero.
   LSI uses a different scheduler (RR no-attack) as baseline; ADI uses the same scheduler.
   FIX: define two clear pairs per scheduler X:
     AttackSlowdown(X) = metric(X, attack) / metric(X, no attack)      (what the attack costs)
     AbsoluteCost(X)   = metric(X, no attack) / metric(RR, no attack)  (what the scheduler costs)
   Keep LSI (benign cpu_bound turnaround) but also LSI_all (all benign classes). Guard zero or
   tiny denominators (add epsilon, report n/a).

F5 [MUST] Time-to-detect is censored.
   Undetected attackers have no TTD. Median over detected-only is biased. FIX: report detection
   rate plus Kaplan-Meier style curve (time vs fraction detected), censor at sim end.

F6 [MUST] Statistics: multiple comparisons.
   9+ experiments x many metrics x 7 baselines will give false positives. FIX: pre-declare
   primary metrics (ADI, LSI, recall at FPR<=5%, TTD), apply Holm-Bonferroni to the primary
   family, mark everything else exploratory. Add bootstrap CIs next to t-CIs (bursty data).

F7 [SHOULD] Guaranteed-share parameters overlap and are not formally reconciled.
   min_share=2%, slot_period=10 (about 10% of dispatches), cap[3]=0.10. FIX: derive one
   formula for the guaranteed lower bound and the cap upper bound, write it in docs, and
   encode it as property tests (see A2).

F8 [SHOULD] Baselines are weak.
   Only a static CPU-share threshold. A reviewer will ask "why not Linux CFS, cgroup cpu.max /
   pids.max, or a learned anomaly detector?" (see A4).

3. ADDITIONS THAT MAKE IT A RESEARCH PROJECT
------------------------------------------------------------------------------------------
A1 [MUST] Formal threat model (new doc: docs/THREAT_MODEL.md, 1 page -> paper Section III)
   - Attacker goals: (a) denial of service to interactive users, (b) resource theft (mining),
     (c) stealth (stay undetected). Attacker knowledge: black-box (sees only own latency/CPU).
   - Capabilities: unprivileged process, can fork, can duty-cycle, can mimic an IO pattern,
     can adapt every 500 ms. Cannot: modify scheduler, kernel exploits, side channels.
   - Out of scope (state honestly): memory/IO/network exhaustion, multi-tenant covert channels,
     privileged attackers.
   - Defender goals: bounded harm to benign work, bounded false-positive cost, no starvation.

A2 [MUST for a,b / SHOULD for c-e] Formal guarantees + property-based tests
   (a) Starvation-freedom: any contained process receives >= m fraction of CPU over any window
       W while others are runnable. Give the bound as a function of slot_period and quantum.
   (b) Work-conservation: CPU idle only if no runnable process.
   (c) Bounded harm: extra delay the contained set can impose on any benign process <= f(caps).
   (d) CUSUM: approximate average run length (false-alarm rate) under Gaussian benign share and
       detection delay for a drift of size delta; compare analytic vs simulated.
   (e) Hysteresis: max level changes per window under bounded noise.
   Implement (a)(b)(e) as `hypothesis` property tests (random workloads, assertions hold).

A3 [SHOULD] Attacker game / stronger N6
   Add a learned attacker (epsilon-greedy bandit or small Q-learning over duty levels 0.1..1.0,
   reward = CPU obtained minus penalty when throttled). Define attacker utility = useful CPU
   gained. Show the long-run attacker utility under each scheduler (SABRE should cap it).
   Also add a MIMICRY attacker (cpu miner padded with fake short IO waits to pose as bursty)
   and report the attacker's throughput cost of evading.

A4 [MUST] Stronger baselines (put into E1)
   - CFS-like scheduler (virtual runtime, weighted fair share) as the "what Linux does" reference
   - RR + cgroup-style limits: hard cpu cap per process + max-children limit (pids.max analogue)
   - RR + learned anomaly detector on the SAME features (IsolationForest, logistic regression
     trained on labelled calibration runs as an upper bound). scikit-learn allowed ONLY in
     experiments/baselines; change Master Prompt rule 1 accordingly.
   - MLFQ with periodic priority boost.

A5 [MUST] Detection-quality curves
   ROC and PR curves by sweeping risk thresholds; report AUC and recall at FPR = 1% and 5%.
   Compare SABRE risk score vs static threshold vs learned detector on the same data.

A6 [MUST] Real-data validation (promote E10 from optional)
   Use a public workload trace (Parallel Workloads Archive SWF, or a cluster trace) for benign
   processes; inject the same attacks. Report whether conclusions hold. Optional small
   real-machine check: psutil advisory mode inside a VM/sandbox only, print recommended nice
   values, never enforce.

A7 [MUST] Robustness and distribution shift (new experiment E11)
   - Calibrate on lognormal workload, test on heavy-tailed (Pareto) bursts and a different
     arrival rate and class mix.
   - Inject classifier noise: 10% / 20% of processes misclassified.
   - Inject feature measurement noise (+-10-30%) and delayed feedback (stale features).
   - Report degradation curves. A method that fails gracefully is a stronger paper.

A8 [SHOULD] Sensitivity analysis done properly
   One-at-a-time tornado chart plus global screening (Morris or Sobol) over ~10 parameters
   (lambda, gamma, thresholds, caps, alpha, q_base, weights). Tune on tuning seeds only.

A9 [SHOULD] Explainability evaluation (N7)
   Check decision-log reason codes against ground truth (does `LVL2_CUSUM` appear for the
   lowslow attacker, `LINEAGE` for fork children?). Report reason-code accuracy and include one
   annotated log excerpt. This turns "decision log" into a measurable contribution.

A10 [SHOULD] Cost-model realism
   Overhead costs (0.02 ms etc.) are assumptions. Micro-benchmark the real Python/NumPy update
   to get an order of magnitude, or cite published eBPF/monitoring overheads; keep E8 as the
   safety net (break-even point).

A11 [MUST] Reproducibility package
   - Seed manifest file: tuning seeds 100-119, calibration 200-219, evaluation 0-29 (disjoint,
     committed).
   - Config hash + git commit hash written into every results CSV row.
   - `make reproduce` (or `python -m sabre.experiments.run_all`) regenerates every table/figure.
   - Dockerfile, GitHub Actions CI, tagged release, Zenodo DOI for the artifact.

A12 [MUST] Related-work matrix and positioning
   Table: columns = prediction / classification / risk scoring / drift detection / lineage /
   reversible containment / overhead charged; rows = papers (Linux CFS, MLFQ literature,
   fork-bomb defences like process limits, cryptojacking detectors, anomaly-detection
   schedulers, ML-based schedulers, CUSUM in intrusion detection). SABRE should be the only row
   with all ticks. Source real citations yourselves; do not accept AI-invented references.
   Verify every reference exists.

A13 [MUST] Limitations section written early
   Simulator not kernel; single core (unless E13); synthetic attacks; assumed cost model;
   cannot see memory/IO attacks. Reviewers reward honesty.

A14 [STRETCH] Multi-core (E13): 2 and 4 cores, global queue; fork bomb and miner behave
   differently. Promote to SHOULD if time allows (it is the first thing a reviewer asks).
